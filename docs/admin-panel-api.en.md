# Admin panel: all routes and API contracts

Documentation of every route in the built-in `telesrv` admin panel — the SPA
page addresses and the API routes behind them. The panel server lives in
`cmd/telesrv-admin`; routes are declared in `(*server).routes()`
(`server.go:50`).

The panel is a plain HTTP server: it serves the built frontend (`/`) and a
JSON API under the `/api/` prefix. Every API path requires a session (cookie),
and every mutating request additionally requires a CSRF token. Many routes also
check an operator permission (`permission`).

## How to use this document

- For each GET endpoint, the **request parameters** (query) and a short **response** shape are listed.
- For each POST endpoint under `/api/actions/*` and the verification decisions, the **request body** (JSON) is given. They all share common fields (see below) plus their own specific fields.
- `int64` in JSON may be sent either as a number or as a string (e.g. `"user_id": "123"` or `"user_id": 123`) — the server accepts both (`flexInt64`). `flexUnix` accepts Unix seconds or a date in `2006-01-02` / RFC3339 form.
- All mutating requests go to the Admin API. A command's response is either `{"status":..., "message":..., "command_id":...}` on success (HTTP 200) or `{"error":..., "code":...}` on error. An optimistic-locking conflict is `409`.

## Authentication and session

| Method | Path | Description |
| --- | --- | --- |
| POST | `/api/login` | Log in. Body: `{"secret": "..."}`. Validates the config secret, issues a signed session cookie and CSRF cookie. The only mutating route without a CSRF token (no session yet); only Origin is checked. |
| POST | `/api/logout` | Log out. Destroys the session and CSRF cookie. |
| GET | `/api/session` | Returns `{"actor": "...", "permissions": [...], "csrf_token": "..."}`. Called by the panel on startup. |
| GET | `/api/public/icon` | The server icon, unauthenticated, so the login page can show it. `404` when no icon is configured (the page then falls back to `/logo.png`). Not cached. |

The session lives in a signed cookie (default TTL 12 hours); there is no
server-side session store. Every request except `GET/HEAD/OPTIONS` and
`/api/login` must present:

- the `telesrv_admin_csrf` cookie;
- the `X-CSRF-Token` header with the same value;
- an Origin matching the host (when Origin is present).

Violating any of the three — `403 Forbidden`.

Most sections are a read/manage pair: the read right opens the page, the manage
right is what the buttons on it need. The panel checks the read right for the
page's own GET endpoints and the manage right per action, so granting only
`accounts.read` gives a working read-only account screen.

A few rights are deliberately independent of the section they sit in:
`verification.review` and `botverification.review` are granted separately
because the two queues are separate mechanisms over separate tables, and
`verification.revoke` is checked *in addition to* `verification.review`.
`admins.manage` is the one right that can hand out every other right, so it is
never implied by anything, and `audit.read` is supervisory rather than riding on
the sections it covers.

The session's permission list is returned from `/api/session`, and the frontend
uses it to decide which sidebar sections to show and which pages to refuse — see
"Navigation and permissions in the UI" below.

## Navigation and permissions in the UI

The panel's sidebar, its in-page tab bars and its route table are three views of
**one declaration**: `cmd/telesrv-admin/web/src/nav.ts`. That file lists every
section, the paths that belong to it, and the right each of those paths enforces
server-side. `Layout.tsx` renders the sidebar from it, `SectionTabs.tsx` reads
each section's tab list from it, and `Routes.tsx` asks it a single question --
`routePermission(path)` -- and gates the whole surface in one place.

Two consequences worth knowing before changing anything here:

- **A section is rendered when the session holds *any* of its tabs' rights**, and
  its link resolves to the first visible tab. An operator holding only
  `prices.manage` gets one Commerce row that opens on Prices. A section reduced
  to a single visible tab draws no tab bar at all.
- **A page can never be advertised and then answer 403.** Before this table
  existed, twelve sidebar entries rendered unconditionally while every endpoint
  behind them was gated -- an operator without `accounts.read` still saw
  Accounts, and clicking it produced a bare 403 rather than the explanation
  `PermissionDenied` gives. The gate is now derived from the same strings the
  sidebar reads.

### Adding a page to the panel

In order, because skipping a step produces the drift this section exists to
prevent:

1. **Decide whether it is a new section or a tab of an existing one.** If the
   page is a sibling of something already there -- it serves the same job over a
   different slice -- it is a **tab**, not a second sidebar row. Commerce already
   holds Prices and the Stars ledger; Media holds Storage; Accounts holds
   Account Rating and Shared devices. A new sidebar row is only for a genuinely
   new job.
2. **Add it to `nav.ts`**, with the right its route enforces server-side. If you
   need a right that does not exist yet, add it to `permissions.tsx`
   (`permissionLabels` *and* `permissionGroups`) and to `assignablePermissions()`
   in `security.go` -- a right that is not assignable cannot be granted, and the
   operator-accounts picker will not show it.
3. **Add the route** in `Routes.tsx`. Do **not** wrap it in `PermissionGate`: the
   gate is already applied from `routePermission`, and a hand-wrapped branch is
   the thing that let the old gaps accumulate.
4. **Add the page** in `web/src/pages/`, render `<SectionTabs sectionId="..." active="..." navigate={navigate} />`
   inside it, and take a `navigate` prop if it needs one.
5. **Translate it.** Every user-visible string goes through `useI18n()` and gets
   an entry in all three language blocks of `i18n.tsx`.
6. **Rebuild the bundle.** `cmd/telesrv-admin/server.go` does
   `//go:embed web/dist`, so `web/dist` is what a non-Docker build ships. Run
   `npm run build` and commit the result, including the deletion of the old
   hashed assets. A `src` change without a rebuilt `dist` does not ship.
7. **Regenerate the tables in this document:**
   `python3 scripts/gen_admin_panel_doc_tables.py --write`.

## Response conventions

- Successful reads — `200` + JSON; files (avatars, animations, previews) — the file itself.
- Errors — JSON of the form `{"error": "...", "code": "..."}` with the corresponding HTTP status.
- `401` — missing/expired session; `403` — CSRF/Origin violation or missing permission (in `requirePermission` the body gets an added `permission` field); `409` — optimistic-locking conflict (moderation case, verification); `502` — Admin API unreachable.
- Errors from commands sent to the Admin API are returned as `{"status": ..., "message": ..., "error": ...}`.

## Common command fields (POST `/api/actions/*`)

Every mutating request carries in its body:

| Field | Type | Description |
| --- | --- | --- |
| `command_id` | string | Idempotency key for the command. Repeating the same `command_id` does not execute the action twice. If empty — generated by the server. |
| `reason` | string | Mandatory operation reason (audit). |
| `confirm` | bool | Operator confirmation (`true`). |

### Setting or resetting a login password

`set-login-password` gives any existing account a login password (phone number
+ password sign-in) or replaces the one it has; the operator never needs the old
password. Use it to give an account that signed up with a login code a password,
or to help a member who forgot theirs.

- **Where:** Accounts → open the account → **Set login password**. The field and
  the "Also sign out all devices" checkbox (off by default) are shown only to
  operators holding `accounts.manage`; the route requires the same right.
- **Flow:** the usual reason → dry run → confirm. The dry run checks the account
  and the password and reports `had_password` (whether this is a set or a reset);
  nothing is written. Confirming writes the password.
- **Rules:** the password is 1 to 256 UTF-8 bytes (`LOGIN_PASSWORD_INVALID`
  otherwise), with no complexity rules. System accounts, bots and deleted
  accounts are refused with `USER_INVALID`. It works while the password login
  switch (`TELESRV_PASSWORD_LOGIN_ENABLED`) is off; the password is then stored
  but cannot be used until the switch is turned on.
- **Effect:** the account can sign in with the new password at once; any login
  challenge issued before (`telesrv.getLoginPassword`) now fails with
  `SRP_PASSWORD_CHANGED`; every session of the account receives a message from
  777000 saying an administrator set or reset the password. With
  `revoke_sessions: true` every authorization of the account is then revoked,
  exactly like `revoke-sessions` with `revoke_all`. If the password was written
  but revoking the sessions fails, the command is still recorded as succeeded
  (the password is set and the notice was sent) with `revoke_sessions_failed:
  true` and `revoke_sessions_error` in its details, and the panel says to revoke
  the sessions separately: running the command again under a new `command_id`
  would reset the password and notify the member a second time. The command
  also finishes when the panel request is cancelled midway, so it is never left
  `running`.
- **Secrecy:** the panel forwards the plaintext over HTTPS to the server, which
  computes the SRP verifier the way clients do and stores only the verifier and
  salts. The request preview masks the field; the password never appears in the
  command log, the audit trail, responses or logs. Idempotency (the same
  `command_id` replayed) compares an HMAC of the password keyed from the server's
  `TELESRV_ADMIN_API_TOKEN`, so reusing a `command_id` with a different password
  is rejected with `COMMAND_ID_CONFLICT`, and the stored fingerprint cannot be
  checked against guesses without that key.
- The limit of 256 bytes is a server bound: the SRP algorithm itself (td,
  Telegram Desktop) has no length limit, and 256 bytes is far beyond any typed
  password.

### Creating an account with a login password

`create-account` takes an optional `password`. Left empty, the command behaves
exactly as before: only the account is created and the member signs in with a
login code. Filled in, the account and its login password are written in one
transaction, so the member can sign in with phone number + password
(`telesrv.signInWithPassword`) right away, without any login code.

- **Where:** Accounts → **Create account** → the optional **Login password**
  field.
- **Atomic:** either both the account and the password are written or neither
  is. An occupied number (`PHONE_NUMBER_OCCUPIED`) or an invalid password
  (`LOGIN_PASSWORD_INVALID`) leaves nothing behind, and a failed password write
  rolls the new account back.
- **Rules and secrecy** are those of `set-login-password` above: 1 to 256 UTF-8
  bytes, the server computes the SRP verifier, the password is masked in the
  preview and never appears in the command log, the audit trail (its details only
  say `login_password: true`), responses or logs. The idempotency fingerprint is
  the keyed HMAC, so reusing a `command_id` with a different password — or
  without one — is rejected with `COMMAND_ID_CONFLICT`. The dry run validates
  the number and the password and writes nothing. No 777000 message is sent: the
  new account has no sessions yet.

### Creating an account with staff permissions

`create-account` takes an optional `permissions` object with the fields of
`set-permissions` (`enabled`, the eleven flags, `send_whitelist`) minus
`user_id`. The account is under permission control from the moment it exists:
the account and its permissions are written in one transaction, together with
the login password when one is given.

- **Given:** the fields given replace the uncontrolled defaults (master switch
  off, every action allowed, whitelist off and empty); fields left out take those
  defaults. For an account that is explicitly not controlled, send
  `"enabled": false`. The whitelist follows the `set-permissions` rules (accounts
  exist and are not deleted, at most 1000, duplicates dropped); an invalid one is
  rejected with `PERMISSION_WHITELIST_INVALID` and no account is created.
- **Not given:** when there is a default permissions template (Accounts →
  Default permissions) a snapshot of it is written; without a template no
  permissions are written. This holds whatever the template's "Also apply to self
  sign-ups" switch says: that switch only concerns self sign-ups.
- **Dry run** validates the permissions too and writes nothing.
- **Records:** the command details and the audit trail carry the permissions
  finally written (`permissions`) and where they came from
  (`permissions_source`: `request` or `defaults`); without permissions neither
  key is present.
- **Where:** Accounts → **Create account** → the collapsible **Staff
  permissions** section. Opening it prefills the shared permission editor from
  the template (or the uncontrolled defaults when there is none), and what it
  then shows is sent as `permissions`. Left unopened, nothing is sent and the
  server applies the template.

## API: machine account lookup (v1)

`POST /v1/accounts/resolve-by-phone` — bearer-token-protected, read-only
account lookup used by the Telegram store bot's "fetch my ID" flow. It resolves
the numeric account ID from a phone number without viewer privacy projection,
so the bot can auto-save a user's server ID when they have already set up an
account there. Unlike every `/api/actions/...` route it carries no command
metadata, because the endpoint never mutates state and writes no audit entry.

| Field | Type | Description |
| --- | --- | --- |
| `phone` | string | Phone in any formatting (spaces, dashes, leading `+`); normalized server-side by `domain.NormalizePhone`. |

Response `200 OK`:

| Field | Type | Description |
| --- | --- | --- |
| `found` | bool | Whether an account with this phone exists. |
| `user_id` | int64 | The numeric account ID; `0` when `found` is `false`. |

Errors: `401` — invalid/absent bearer token; `500` — lookup failure;
`501` — deployment built without a lookup backend. Missing numbers are a
success with `found: false`, never `404`.

Example:

```http

```

## Gift inventory when importing or replacing a revision

For a new official gift, enabling `include_collectible` uses `supply_total` as
both the unique-gift supply and the base gift's initial sales cap. If omitted,
the collectible supply is derived from the snapshot's availability or upgrade
variants. With collectible import disabled, this input does not limit ordinary
base gifts. Auctions still require their own finite supply.

An existing `gift_id` keeps its original base supply, limited flag, remaining
stock, resale counters and sale dates. Replacement never replenishes exhausted
stock or converts it to unlimited. A different base cap or auction/non-auction
mode requires a new gift identity; requesting it on an existing identity fails
without publishing either revision. The separate collectible-pool editor does
not change base stock. Inventory is rechecked under the purchase/catalog lock
at execution, and the result reports the committed remaining stock. Dry-run
does not reserve stock. The catalog badge shows remaining / total copies.
